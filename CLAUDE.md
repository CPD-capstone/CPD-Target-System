# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ESP32 firmware for the Cookeville Police Department shooting range's target control system, used for shooting qualifications. It is a from-scratch rebuild of a dead 1995 Action Target pneumatic pop-up system: the ESP32 hosts its own WiFi access point and captive-portal web UI, and range staff use it to raise/hide **20** pneumatic turning targets and run timed drills. Requirements and the wiring diagram live in `docs/requirements/` and `docs/architecture/` (PDFs); the hardware design history is in `docs/AI/CPD_Range_System_Context.md` (summarized under **Physical system** below).

## Commands (PlatformIO)

```sh
pio run                      # build firmware (env: esp32)
pio run -t upload            # flash firmware
pio run -t uploadfs          # build + flash the LittleFS image from data/ (web UI + database.json)
pio device monitor           # serial monitor @ 115200
```

**Testing the web UI without the ESP32:** `data/controller-test.js` is a fake controller kept commented out (with its loader in `script.js`) so it never ships active. To use it, re-enable both (or serve `data/` through a small local server that uncomments them on the fly), open `http://localhost:8000/targets.html?test=1`, and press **Clear** on the small yellow TEST MODE badge in the bottom-left corner after changing `database.json` (the fake keeps its copy in `sessionStorage`). It mirrors the drill/stage/officer API but not every firmware detail (no final-stage hold, no hardware timing). When you add or change an API route the UI uses, update it too.

Changes to anything in `data/` require `uploadfs`; firmware upload alone does not update them. **`uploadfs` replaces the whole LittleFS image, including `database.json`**: officers, scores, drills and defective-target flags entered from the phones are reset to `data/database.json` (a firmware upload keeps them). There is no test suite or linter configured. The UI is plain HTML/JS/Bootstrap with no build step.

`platformio.ini` targets `esp32-s3-devkitc-1`, configured for the board actually purchased: a **Hosyond ESP32-S3** dev board (DevKitC-1 pin layout, 44-pin) with an **ESP32-S3-WROOM-1 N16R8** module (16 MB flash, 8 MB octal PSRAM, so `memory_type = qio_opi` and the 16 MB partition table). The project moved here from the classic ESP32-DevKitC-32E (`esp32dev`). Flash and monitor through the USB-C port labeled **COM/UART**, not the native-USB port. Pin labels are printed on the bottom of the board.

## Physical system

What the firmware drives, and design decisions that constrain it. All hardware has arrived and the control box is being built and wired. Items marked **(bench-verified)** have been confirmed on the bench with the real ESP32-S3, expanders and relay boards; everything else is still the design as drawn, not yet tested end to end (field wiring, valves and air are not hooked up yet).

- **Signal chain:** ESP32 → SPI → 2× MCP23S17 (bare DIP-28 chips, socketed) → 3× SainSmart 8-channel relay modules (Songle SRD-05VDC-SL-C, opto-isolated, VCC–JD-VCC jumper removed) → relay NO contact → 3 A fuse → 1N4007 flyback diode + S14K25 MOV (at the control box end, cathode toward NO — verified on the diagram) → field connectors → ~50-yard original 1995 buried cable → **MAC 46A-AA2-JDDA-1BA** 12 V pilot valves (62.6 Ω, ~0.23 A each), which route compressed air to each target's cylinder.
- **Power:** Tripp Lite PR-40 (13.8 V) → terminal blocks → relay contacts/solenoids; Pololu D24V50F5 (fixed 5 V, 5 A) → relay coil side (JD-VCC) **and** relay logic side (VCC). The ESP32 and both MCP23S17s (VDD) run from 3.3 V. At 5 V VCC, a 3.3 V HIGH from the MCP leaves too little voltage across the relay input's LEDs to light them, so HIGH = off and LOW = on.
- **Control location:** electronics sit indoors in the control tower, ~50 yards from the targets. **There is no physical stop button** (too far to run one); Stop exists only in the web UI.
- **Fail-safe direction:** an unpowered valve **hides** its target. The relay's normally-open contact plus spring-return valves mean any power loss hides every target — this is intended and relied on.
- **Relay polarity (bench-verified):** the SainSmart boards are active-low (IN pulled LOW = relay on); all three are physically matched, and relays switch the right way from the web UI. `RELAY_ACTIVE_LOW` in `pins.h` is applied only in `hal.cpp`'s `writeOutputs()`; everywhere else, a set mask bit means "valve powered = target facing." `initSPI()` loads the all-off pattern into the output latches **before** switching pins to outputs — otherwise every relay energizes at boot. Keep that order.
- **Air lines are plumbed so an unpowered valve hides its target (verified).** Never compensate for plumbing in firmware — firmware can't make an unpowered valve safe.
- **Channel map (bench-verified, as built):** MCP1 is wired fully reversed: target n → MCP1 pin index 16 − n, so GPB7–0 → relay #2 → targets 1–8 and GPA7–0 → relay #1 → targets 9–16; MCP2 GPA7–4 (reversed: GPA7 = target 17 … GPA4 = target 20) → relay #3 IN1–4 → targets 17–20. MCP2 GPA0–3 are unconnected; the firmware drives them as outputs held off. Relay #3 IN5–8 are unused. MCP2 GPB0–7 are unconnected (reserved: status LEDs, interlock, expansion). Both chips: A0–A2 to GND, RESET to VDD, separate CS lines, 0.1 µF decoupling across VDD/VSS.
- **Field connectors:** 2× 12-pin ZBLZGP SP21 (24 positions: 20 target lines + ground return split across spares so no 5 A pin carries the ~4.6 A total). Unplugging them is the lightning mitigation — a full surge/grounding system was deliberately scoped out (NFPA 780, licensed professional). **The pin-to-target table in `pins.h` is dummy data**: the field wires are unlabeled and run under concrete, so they must be traced on site.
- **`MECHANICAL_BUFFER` (500 ms per target) is mandatory** — flipping a target again sooner shears its pins. The 500 ms value is an arbitrary safe margin and may be tuned, but the buffer must never be removed or bypassed.
- **SPI wiring (bench-verified):** `pins.h` uses the S3's FSPI pins — SCK 12, MOSI 11, MISO 13, CS 14 (board #1) / 10 (board #2), all on DevKitC-1 header J1 (pins 16–20) — with 10 kΩ pull-ups on both CS lines so the expanders stay deselected while the ESP32 boots. Both expanders pass the HAL health check at boot. The wiring diagram must be updated to match (v3.6 still shows the classic-ESP32 pins 16/17/18/19/23, the old CS order and the old channel map). If the two ever disagree, `pins.h` is authoritative.
- **Bring-up lesson:** if an expander reads back only `0x00` or `0xFF` (whatever MISO's pull resistor gives), the chip isn't driving SO — check the SO (pin 14) → GPIO 13 joint first. During bring-up that wire was unsoldered yet still passed a continuity test, because probe pressure made contact.
- **USB:** the board only enumerates as a serial port (CH343, COM/UART port) with the USB-C cable in one orientation; if no COM port appears, flip the cable or use a USB-A to USB-C cable.

## Architecture

Module per concern, each with a header in `include/` and implementation in `src/` (note: `web_server.h` ↔ `src/webserver.cpp`):

- **wifi_manager** — Starts a soft AP (`SSID "CPD Range Control"`). Password persisted in NVS via `Preferences` (namespace `wifi_config`, key `ap_pass`), defaulting to `DEFAULT_PASSWORD`. Passwords < 8 chars are rejected (WPA2 minimum).
- **webserver** — `ESPAsyncWebServer` + a `DNSServer` wildcard that resolves every hostname to the AP IP. The OS connectivity probes (`/hotspot-detect.html`, `/generate_204`, `/connecttest.txt`, …) get their "online" replies on purpose, so phones **don't** open the captive-portal mini-browser (fixed OS header, wipes localStorage on close); staff use a Home Screen icon instead (`data/manifest.json`, `apple-touch-icon.png`). The trade-off: phones send all traffic over this WiFi while joined. `/` and `/redirect` serve `targets.html`; `/api/*` goes to the REST API; everything else is served statically from LittleFS (unknown paths fall back to `targets.html`). `loop()` only pumps DNS via `processCaptivePortalDNS()`.
- **api** — JSON REST routes, registered by `registerApiRoutes()` before `serveStatic`. The route list is in `api.h`. ESPAsyncWebServer matches handlers in registration order and `/a` also matches `/a/b`, so sub-paths must be registered before their parents. JSON bodies need `Content-Type: application/json`. Unmatched `/api/*` returns a JSON 404.
- **database** — LittleFS-backed JSON store in `/database.json`. Each CRUD function loads the whole file, mutates it, and writes atomically (write `/database.tmp` → remove → rename). `get*` readers load only the needed section with an ArduinoJson filter.
- **hal** — Hardware layer for the expanders and relays (see **Physical system** for wiring). The range has exactly **20 targets** — use `NUM_TARGETS` (`hal.h`), never a literal. SPI is on the S3's FSPI pins (SCK 12, MOSI 11, MISO 13) with CS on GPIO 14 (board #1) / 10 (board #2); avoid GPIO 26–32 (flash/PSRAM), 33–37 (octal PSRAM on this N16R8 module), strapping pins (0, 3, 45, 46), 19/20 (USB) and 43/44 (UART0). Pin map, relay polarity and the (dummy) field-connector table are in `pins.h`.
- **target_manager** — Drill execution API for the web layer: `executeDrill(name, targetMask)` (returns a `DrillStartResult` reason), `pauseDrill()` (freezes the drill clock; a delay keeps its remaining time), `resumeDrill()`, `stopDrill()`, `resetTargets()`, `getDrillState()`, `getDrillStatus()` (name, step progress, last `DrillOutcome`, stop latch), and `setTargets(mask, present)` for manual raise/hide, which claims the same `runnerBusy` flag so it is refused while a drill runs. **`stopDrill()` is the operator's emergency stop and must never move a target**: it freezes the HAL via `hal_hold()` (discards queued commands and cooldown-pending flips, leaves outputs as-is), ends the drill without the usual final hide, and latches until `resetTargets()`, which releases the hold and hides all targets. `executeDrill` reads `/database.json` (filtered to `drills` + `targets`), recursively inlines nested drills into a flat step list, excludes targets with `working: false`, and hands the list to a persistent `DrillRunner` task (core 1, priority 4). The runner sleeps on FreeRTOS task notifications (START/RESUME/STOP/PAUSE bits) so `pause` waits for the operator and stop interrupts any delay; it hides the drill's targets when it completes or fails, but not after an emergency stop. Drill delays are timed from when targets are *fully facing*: after `present`, the runner waits until `hal_getTargetStates()` shows every target fired, then the **target flip delay** (`getFaceTravelMs()`): set in Settings, saved in NVS (namespace `drill_config`, key `face_ms`, 0–5000 ms, loaded by `loadDrillSettings()` in `setup()`), exposed as `GET`/`PUT /api/settings/target-flip`; `TARGET_FACE_TRAVEL_MS` in `hal.h` is only the default (300 ms, measured on the real targets). Like the WiFi password, it survives `uploadfs`. **Stage navigation:** each direct child drill of a full drill is a *stage*; a drill with no stages is split into *parts* at its yield steps (`DrillStatus::stagesAreParts`), and parts inside a stage are reported as `partIndex`/`partCount`. `jumpToStage(Previous|Current|Next)` (Back / Redo / Skip; `resetDrillStage()` is `Current`) works while running or paused: the runner hides the drill's targets, waits out `MECHANICAL_BUFFER`, moves to the first step of that stage and waits for Resume (`stageRestartReady`). Between stages (at the yield after stage *k*), Next skips the upcoming stage. `jumpToStagePart(stage, part)` (`POST /api/drill/jump`) goes to a given stage and part (the UI's part chips and jump list); both queue the move through `queueJump()`. A full drill holds paused after its last stage (`finalStageComplete`) so it can be redone; Resume ends it. Exposed over HTTP as `/api/stop`, `/api/reset`, `/api/drill/*` (including `previous-stage`, `reset-stage`, `next-stage` and `jump`) and `/api/targets/{present,hide,state}`.

### Target actuation flow (cross-core)

Nothing outside `hal.cpp` touches SPI or the queue directly (the expander objects are private to `hal.cpp`) — use `hal_sendCommand(targetMask, newState)` and `hal_getTargetStates()`. Targets are handled as 20-bit masks (bit 0 = target 1; `targetBit(n)`), so one `TargetCommand` moves a whole group. `SolenoidControlTask` (core 1, priority 5) applies queued commands to a desired mask every 10 ms, flips only targets past the per-target `MECHANICAL_BUFFER` cooldown, and writes each expander in one SPI transaction so a group flips simultaneously.

**Expander health check:** Adafruit's `begin_SPI()` never talks to the chip, so the HAL verifies each expander itself (`Expander` subclass in `hal.cpp` adds raw register access): at startup and every `HEALTH_CHECK_MS` (1 s) it round-trips test patterns through DEFVALA (unused — interrupts are never enabled) and reads back IODIR/OLAT against what it wrote. A failure (chip missing, or reset by a power glitch so its pins reverted to inputs) sets `expanderFailed`, and the solenoid task deletes itself **without writing anything** — a write into an unknown state could move targets. `hal_isReady()` then stays false until reboot, so drills fail, the API returns 503, and `/api/drill/status` reports `hardwareReady: false`.

`hal_init()` runs at the start of `setup()`. The pin map, relay polarity and SPI are bench-verified; the target flip delay is measured (0.3 s); the field-connector pinout is still unmeasured.

### Web UI (`data/`)

Static pages (`targets.html` — shown to users as **Range Control** in its title, the menu and help text; the file name stays so `/` and existing links keep working — `drills.html`, `Performance.html`, `settings.html`) share `script.js` / `style.css`; Bootstrap, its icons and the banner font are vendored (gzipped) in `data/vendor/` because the AP has no internet. The **controller is the source of truth** for drills and targets: every page polls `GET /api/drill/status` (500 ms while a drill is running or paused, 3 s idle) and redraws the status bar, drill buttons and target cards from it; there is deliberately no WebSocket (one phone at a time, and suspended/dropped connections need no reconnect logic). Start/Pause/Resume, manual raise/hide, Stop and Reset are ordinary POSTs, so polling never delays them. **Stop** while a drill runs is the emergency stop (freeze in place; a Reset button then appears); while the drill is **paused** it ends the drill (stop + reset, hiding its targets). Start/Resume wait for a cancellable countdown (Settings: instant / set time / random 1–5 s, saved per phone; Targets shows the current setting under the drill buttons with a link to `settings.html#startDelay`). The status bar has two lines (drill name small, state large: blue idle, dark while a drill runs or is paused, red for a latched Stop or hardware fault, amber in manual mode), sticks to the top while a drill is active, and names the stage and part from `/api/drill/status`; other stages' names come from the drill's own sequence (`drillStageNames()`), part counts from `stagePartCount()`, and `stageJumpTargets()` mirrors `stageJumpTarget()` in `target_manager.cpp` — keep those in sync. On Targets: **Stop sits in a bar pinned to the bottom of the screen** whenever a drill is active or a start delay is counting down (not in manual mode), and the same spot holds Reset after a Stop; Start/Resume and Pause share one slot; a compact stage control (‹ current stage › Redo, plus one chip per part of the current stage; tapping the stage name opens a list to jump to any stage or part) replaces separate Back/Redo/Skip buttons; the drill description is collapsible (per tab). The drill buttons appear once a drill is selected, the manual group buttons only in manual mode, and the View card (grid/list, Hide defective, Filter targets) is collapsible. The selected drill and its confirmed targets survive page changes (sessionStorage). Drills whose present/hide steps use "all targets" (or `random`) ask which targets to use: the picker opens when the drill is selected, defaults to the targets the last drill ran on (the controller's idle `status.targets`, RAM only, so all after a power cycle), and **Confirm targets** returns to the page, where Start drill runs on them. Drill descriptions show on Targets with a drill selected and while paused, with the `Part n` line that runs next highlighted; a full drill's own description (a qualification's overall rules) shows only on its Drills page card. Defective targets (the controller's `working` flag) and officers (name and badge number) are edited in Settings. **Qualifications** (Pistol, Rifle, SWAT plus custom ones) are one shared list: they group drills (each drill's `qualifications` tags; a full drill also counts under its stages' tags) and the scores officers earn on Performance. The Drills page's only filter is a chip row (All / each qualification / No qualification); *Manage qualifications* adds them and deletes custom ones (`DELETE /api/qualifications`, refused for the built-in three and while any officer has scores under it; deleting untags its drills). Each drill card shows a "Pistol · Full drill" badge (Full drill / Stage / Custom is the drill's kind, not a filter), and the Targets drill dropdown is grouped by qualification. Drills are created and edited on the Drills page with a drag-and-drop sequence builder (SortableJS, vendored) and saved on the controller through `/api/drills`; `present`/`hide` steps use either all of the run's targets or their own `targets` list. Only per-phone preferences (start delay, grid/list view, View card open, manual mode, theme) live in localStorage. **Theme** (Settings): Normal, or Tactical — `data/tactical.css`, every rule scoped under `html.theme-tactical`, with Bootstrap's `data-bs-theme="dark"`; an inline script in each page's `<head>` applies the saved theme (`cpd-theme`) before the page draws. When adding UI with hard-coded light colors, give it a Tactical override in `tactical.css`. After changing `script.js`, bump its `?v=` cache-buster in all four HTML pages. The Performance page loads officers from `GET /api/officers?today=…` and shows the controller's 12-month stats.

## Database schema

`data/database.json` is the **authoritative** schema: top-level arrays `qualifications` (names; Pistol/Rifle/SWAT plus custom ones added and deleted through `/api/qualifications`; filled with those three if missing), `Officers` (keyed by `BadgeNum`, with `pistol/rifle/swatQualScores` as newest-first `[score, "YYYY-MM-DD"]` pairs, and custom qualifications' histories under `qualificationScores: {name: [...]}`), `drills` (`drillName` + `sequence` of steps whose `action` is `present`/`hide` (optional `targets: [n, ...]`, default all; `present` may instead have `random: n` — n targets picked by the controller each time the step runs), `yield` (hands control back to the operator until Resume/Start; called `pause` before — firmware, database validation and UI still read old `pause` steps as yield, and the UI saves them as `yield`), `delay`+`timeMs` (whole ms), or another drill's name for composite "Full Drill" entries; drills may carry `qualifications: [name, ...]` (the built-in ones are tagged Pistol / Rifle / SWAT); the shipped drills also carry `"builtIn": true`, which the UI uses to list them as Stages rather than Custom — `addDrill()` never stores it, so drills made on the Drills page never have it; any drill may have a `description` (≤ 2000 bytes; the built-in qualification stages carry the department qualification sheets' text with each timed section labelled `Part n (t s):`, and each full drill holds that qualification's overall rules), and `targets` (`{id, working}`). The roster officers were added with **placeholder badge numbers 90001–90073**; replace them with real ones in Settings (Edit) as they become known.

## Known issues / open items

- **Still to measure on hardware:** the field-connector pinout (trace the buried wires on site), and that the expander health check trips when a chip is pulled from its socket.
- An ESP32-only reset (crash/brownout) with the expanders still powered leaves relays in their last state until `initSPI()` runs, which then turns them all off (targets hide).
